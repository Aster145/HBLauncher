# NES for HBLauncher (test build)

Build one or two locally supplied ROMs as HBLauncher entries:
`NES 1 (Test)` and `NES 2 (Test)`. No game ROMs or ROM-containing packages are
included. The builder leaves your original ROM files unchanged.
The source folder stays hidden in the launcher until you build it.

## Playing

Return to the HBLauncher menu, tap **Refresh** at the top right after a rebuild,
select either NES entry, and press **A**. On the Mario title screen press **+**.
Keep the Windows launcher process running.

| Controller | Action |
| --- | --- |
| D-pad / left stick | Move |
| A | Jump (NES A) |
| B / Y | Run (NES B) |
| + | Start |
| L | Select |
| X | Pause / resume emulator |
| R | Reset game |
| - | Return to HBLauncher |

Disconnecting the controller pauses emulation; reconnect and press X to resume.
The app has no audio or save-state support. Returning to the menu or resetting
starts the game over.

## Supported format

This is a GPU emulator written in GLSL for the HBLauncher GPU-app ABI, not a
Switch NRO. It accepts NTSC iNES mapper 0 (NROM), 16/32 KiB PRG ROM and 8 KiB
CHR ROM or CHR RAM. Other mappers, NES 2.0 headers, trainers and four-screen
mirroring are rejected. Development testing used two Chinese text/graphics
variants of Super Mario Bros.; other NROM games are not guaranteed to work.

The CPU implements all 151 official Ricoh 2A03 opcodes and selected NOPs. The
PPU uses scanline snapshots, with scrolling, sprites and sprite-zero events.
It approximates timing rather than reproducing every PPU dot or bus cycle.

## Build and validation

Install Python with Pillow, `glslangValidator`, and `spirv-val`. The builder
honors `PYTHON`, `GLSLANG`, and `SPIRV_VAL` environment variables, then checks the
optional local Windows tools under `tools/`, then uses commands on `PATH`.
Set `NES_FONT` (or `HB_FONT`) to a font with Simplified Chinese glyphs if Microsoft
YaHei or Noto Sans CJK is unavailable. Tool binaries and fonts are not bundled.

From the HBLauncher directory in Windows PowerShell, use your own ROM paths:

```powershell
node .\apps\nes\build.cjs "C:\ROMs\first.nes" "C:\ROMs\second.nes"
```

The second argument is optional. The second package is generated in
`apps/nes-2/`; shared source stays here. Generated `assets/data.bin` files embed
the ROM, and are ignored by Git along with the generated app packages.

Desktop checks need a Vulkan driver and the `game-compute-check` / `game-render`
harnesses built from `homebrew-launcher/game-compute-check.c` and `game-render.c`.
The script `scripts/build-checks.sh` builds these with a C compiler and Vulkan
development headers/libraries on Linux. On Windows, build the same sources
against the Vulkan SDK, or use locally built Windows harnesses. Use
`HB_COMPUTE_CHECK` and `HB_RENDER` to select the executables, or place them on
`PATH`. The previous local Windows tool layout under
`tools/glslang/desktop-tests/` is also recognized.

CPU and PPU tests use synthetic fixtures and require no game ROMs:

```powershell
node .\apps\nes\tests\cpu-check.cjs
powershell -NoProfile -ExecutionPolicy Bypass -File .\apps\nes\tests\run-ppu-test.ps1
```

The integration checks below require both generated packages and expect the
Super Mario Bros. RAM layout; they are not a generic NROM compatibility test:

```powershell
node .\apps\nes\check.cjs
```

The checks execute the production GLSL/SPIR-V on a desktop Vulkan GPU.
Integration results and rendered frames are in `runs/nes-check/`.
Desktop tests do not establish Switch speed or compatibility.

## Device verification and performance

The first device attempt timed out while compiling the compute pipeline. Sharing
one interpreter call site and specializing stack/zero-page accesses fixed that
launch failure: the user confirmed play, and OBS showed Mario in level 1-1.
The launcher recorded 60 frames per 3 seconds, approximately 20 FPS.

The next optimization caches CPU registers between execution-budget boundaries
and reuses nametable/attribute reads in PPU scanline snapshots. On an RTX 4080
SUPER, the same 300 emulated gameplay frames took 3.790545 seconds before and
2.272664 seconds after the change (1.67x compute throughput). Both runs produced
identical complete emulator state. This excludes rendering and pipeline creation;
the speedup on Switch still needs measurement.

The development run passed 194 CPU fixtures, 94 PPU assertions, 3,072 old/new
snapshot comparisons and 12 ROM integration checks. The optimization changes
only the app, not the launcher timeout or connection setup.

Historical performance fixtures and logs are not included: the full emulator
state contains ROM data. To compare your own baseline and current shader on the
same GPU, provide a baseline shader and full 8 MiB state (for example, the
`runs/nes-check/latest.bin` generated by an integration run):

```powershell
node .\apps\nes\perf-check.cjs "C:\NES-test\baseline.comp.spv" .\runs\nes-check\latest.bin
```

An optional third argument selects the optimized shader; the default is the
locally built `apps/nes/app.comp.spv`. Both shaders must use the same state layout.
The script compares 300 frames with connected, idle input, requires byte-identical
final state, and writes `runs/nes-perf/result.json`. Your inputs will produce a
new comparison, not a reproduction of the historical measurement above.
